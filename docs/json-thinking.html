JSON Thinkv0.1.5

Reason first, then emit a single valid JSON value. The model thinks in plain text, and only the answer is forced through a JSON grammar — so you get structured output without throwing away the reasoning step.

How it works

A grammar binds the sampler from the very first token and can't detach mid-stream. Since the default model thinks in <think>…</think>, constraining the whole generation to JSON would forbid reasoning. So a JSON request runs two sequential generations on one engine context, sharing the request's max_tokens budget:

Phase 1 · reason

Unconstrained thinking

The model reasons freely. These tokens ride reasoning_content, never content. The phase stops at </think>, the first visible answer token, EOS, or the budget cap.

Phase 2 · constrain

Grammar-guided JSON

A second generation on the same context attaches a JSON grammar and emits the answer as content — guaranteed to parse. The reasoning carry-over is masked, so the model never re-opens a <think> block.

In the app this is the built-in JSON Think profile. Over the HTTP API it's the OpenAI-shape response_format field — no special client required.

Request

The endpoint is the engine's loopback port (see the Local API view in the app for the live base URL and served model id). The request model must equal the served id from GET /v1/models. No auth header — the engine is loopback-only and unauthenticated.

Any JSON object — {"type":"json_object"}

# BASE = http://127.0.0.1:<ephemeral-port>   model = served id from GET /v1/models
curl "$BASE/v1/chat/completions" \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "<served-model-id>",
    "messages": [{"role": "user",
                  "content": "Return the first three primes. Use the key \"primes\"."}],
    "max_tokens": 512,
    "response_format": {"type": "json_object"}
  }'

A specific shape — {"type":"json_schema"}

Constrains the answer to your JSON Schema. The schema's root must be an object (or a nullable-object union). A scalar/enum/composition root is rejected with 400 so a bare value can't slip through.

    "response_format": {
      "type": "json_schema",
      "json_schema": {
        "name": "answer",
        "schema": {
          "type": "object",
          "properties": {"answer": {"type": "string"}},
          "required": ["answer"],
          "additionalProperties": false
        }
      }
    }

Response

The reasoning lands in reasoning_content; the answer in content is a complete, parseable JSON value with no <think> leak.

Non-streaming ("stream": false)

{
  "choices": [{
    "index": 0,
    "message": {
      "role": "assistant",
      "reasoning_content": "The first three prime numbers are 2, 3, 5…",
      "content": "{\"primes\": [2, 3, 5]}"
    },
    "finish_reason": "stop"
  }],
  "usage": { /* prompt + both phases */ }
}

Streaming ("stream": true)

Reasoning deltas arrive on delta.reasoning_content; the JSON answer streams as delta.content. Concatenate the content deltas to rebuild the value.

data: {"choices":[{"delta":{"reasoning_content":"The first three primes…"}}]}
data: {"choices":[{"delta":{"content":"{\"primes\": "}}]}
data: {"choices":[{"delta":{"content":"[2, 3, 5]}"}}]}
data: [DONE]

Tiny-budget caveat. The two phases share one max_tokens budget. If the budget is too small, a thinking model can spend it all reasoning and reach Phase 2 with no room to emit the answer.

Rather than returning a deceptive 200 with an empty (invalid) body, the engine fails the request with an error envelope carrying json_empty_output. The fix is to raise max_tokens (Phase 2 is guaranteed a small floor, but reasoning-heavy prompts still need headroom). Reproduce it with something like "max_tokens": 16.

Rejected requests (400)

RequestWhy it's rejected
A JSON mode plus a forced tool_choice Each pins the sampler to a different grammar; they can't compose. Send one or the other.
json_schema with a non-object root
(enum, const, anyOf, a scalar type, …)		 Would compile to a grammar a bare scalar satisfies. The answer must be a JSON object, so declare "type":"object".
Any other response_format.type response_format_unsupported — v1 honors json_object, json_schema, and text (the unconstrained default).

In the app

Pick the JSON Think profile in the toolbar and send a prompt — same model as Chat, so switching to it is an instant, no-reload swap. The grammar (not the system prompt) is what guarantees valid JSON.

Self-contained — no server, no network. Source of truth: Inferlets/chat-apc/src/chat/completions.rs (wire contract) and Shared/ProfileStore.swift (the JSON Think profile).
